# Money rounding: the client/server contract

**Decided:** 2026-09-19
**Rule:** the server is authoritative. The client's job is to predict the
server's number exactly, never to be "correct" on its own terms.

---

## The bug

`PriceConverter.toFixed` truncated:

```dart
return (((val * mod).toPrecision(digits)).floor().toDouble() / mod);
```

`10.999` became `10.99`. The backend rounds the same value to `11.00` and
charges that — `PlaceNewOrder.php` uses PHP `round()` for `order_amount`,
`delivery_charge`, `total_tax_amount`, coupon and store discounts, and every
per-item `price` and `total_add_on_price`.

So the customer was quoted one total and billed another, on every order, biased
in the customer's favour by up to one minor unit. `toFixed` feeds all 209
`convertPrice` call sites, so this was every price in the app.

## Why `.round()` alone was not the fix

Dart's `double.round()` works on the binary value. PHP's `round()` applies a
pre-rounding correction (`_php_math_round`, ext/standard/math.c) that undoes
IEEE-754 representation error first. They disagree exactly where money lives:

| value | PHP `round(v,2)` | Dart `(v*100).round()/100` |
|---|---|---|
| `1.005` | **1.01** | 1.0 |
| `8.995` | **9.0** | 8.99 |
| `2.675` | 2.68 | 2.68 |
| `10.999` | 11.0 | 11.0 |

`1.005` is really `1.00499999999999989…`, so `* 100` gives
`100.49999999999999` and a naive round goes down. PHP notices the value is
within representation error of the `.5` boundary and corrects before rounding.

`toStringAsFixed` is not the fix either — it mismatched PHP on 5 of 12 probe
values.

## What we did

`roundLikeServer()` in `lib/util/money.dart` ports PHP's algorithm. It is
verified against **51 vectors generated by PHP itself**.

Regenerate the vectors whenever the backend's PHP version changes:

```bash
php tool/generate_rounding_vectors.php > test/contract/fixtures/rounding_vectors.json
flutter test test/contract/rounding_parity_test.dart
```

CI runs that test as `money-parity-guard`, plus a grep that fails if truncating
money math reappears. **A failure there is a release blocker**: it means the
client and server disagree about what a customer will be charged.

## The longer-term fix: integer minor units

Rounding parity fixes the symptom. Floats are still the wrong type for money —
summing a 30-line grocery cart accumulates error, and the displayed total can
drift from the sum of the visible lines.

`Money` (same file) holds an integer count of piasters. Addition, subtraction
and quantity multiplication are exact; rounding happens once, at the formatting
edge.

```dart
final line  = Money.fromMajorUnits(19.99);
final total = line * 3;              // exactly 59.97, no drift
final vat   = total.percent(14);     // half-away-from-zero, like the server
```

**New pricing code should use `Money`.** `roundLikeServer` exists for the
boundary where doubles still arrive from JSON. The migration target is
`CheckoutCalculationHelper` — 655 lines of float arithmetic with 202 null
assertions — which is scheduled for the pure-function refactor in Phase 3 of
`architecture_hardening_plan.md`. Do that refactor on top of `Money`, not
alongside it.

## Rules

1. **Never** reintroduce `.floor()` or `.ceil()` on a scaled price.
2. **Never** "simplify" `roundLikeServer` to `(v * 100).round() / 100`. The
   contract test will fail, and it will fail for a reason.
3. If the backend's rounding changes, regenerate the vectors **first**, watch
   the test fail, then change the client. Never the other way around.
4. New money arithmetic uses `Money`, not `double`.
